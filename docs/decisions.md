# Decisions

Which libraries `artifacts` uses, and the patterns the code follows. The design is in [design.md](design.md); the
security invariants these decisions keep are in [threat-model.md](threat-model.md), and the IDs below refer to it.

A dependency is taken where writing the code would be maintenance without a security or protocol reason, and refused
where the exact rule is the point (host classification, path decoding, the ID format, logging).

## Patterns

| Concern       | Pattern                                                                                                                                                                                                                                 |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Operations    | One module holds the operations. Each takes validated input, the token name and its dependencies, and returns a result. The REST and MCP adapters decode, call and encode only (P5).                                                    |
| Results       | A discriminated union, `{ ok: true, ... }` or `{ ok: false, code }`, the code from a closed set; one `Record` maps each code to an HTTP status and an MCP tool error, so a code without a mapping does not compile.                     |
| Closed sets   | An `as const` array, the union derived from it, and a `Set` of it for checks at run time; per-member handling is a `Record<Union, ...>` table.                                                                                          |
| Configuration | `parseConfig(env)` returns a result with a closed set of codes; the checks live once and serve the Worker and the deployment script (HOST-2, ACC-2).                                                                                    |
| Routing       | `routeOf(request, config)` classifies by exact host checks and returns a union; `fetch` switches over it exhaustively. A `HEAD` gets the `GET` response. A thrown error answers 500 and logs its class only (DATA-1).                   |
| Input shapes  | A zod schema per input, shared by REST validation and the MCP tool; issues leave validation as `{ field, reason }` with reasons from a closed set. Checks across entries (duplicate paths, the merged entry file) run in the operation. |
| Bounds        | Every bound names its unit (bytes, UTF-8 bytes, files) and the reason that sets it; its test measures in that unit, at and one past the bound (RES-1).                                                                                  |
| SQL           | Every value is bound; no statement has more than 100 bound parameters, so `version_files` rows go in chunks inside the commit's `batch()` (VER-2).                                                                                      |
| Storage waits | The Access key fetch, R2 calls and D1 reads run under a timeout; the D1 commit does not (RES-2). R2 writes are content-addressed: `head` first, `put` if missing, a rate-limited `put` retried twice after a second.                    |
| Logging       | `logEvent(event, fields)` with fields from closed sets (DATA-1).                                                                                                                                                                        |
| Tests         | Tests name the invariant or plan-layer ID they pin (for example `// ISO-2`, `// PL-21`) and test behavior; source checks are kept for the logging sink and the deployment configuration.                                                |
